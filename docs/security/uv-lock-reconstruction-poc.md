# POC: uv universal lock and clean Python reconstruction

- **Issue:** #86
- **Scope:** Windows x64, CPython 3.12 and 3.15
- **uv candidate:** 0.13.7 (pinned for this experiment; not yet an approved CPIE tool)
- **Status:** two local clean reconstructions passed on both target lanes; three consecutive Python 3.12 workload repetitions were stable (2.006837–2.028404 s); CI run #17 for HEAD `121c91cd705997345afce4ba12b54e2100445c50` completed successfully with four jobs and four evidence artifacts; SBOM, vulnerability and license audits remain pending.
- **Manifest/lock:** `poc/supply-chain/python/pyproject.toml` and committed `uv.lock`.

## Objective and boundary

Determine whether one universal `uv.lock` can represent the tested Windows CPython 3.12 and 3.15 lanes while keeping the PyTorch CPU extra restricted to Python 3.12.

This is an isolated POC manifest under `poc/supply-chain/python/`. It is not the production CPIE dependency manifest and does not approve any package version or uv as a project baseline.

## Dependency scope

- The base project lists direct dependencies used by the quantitative workload probe, pinned to the versions observed in the successful local Python 3.12.10 workload.
- The `compatibility` dependency group contains additional direct imports exercised by the compatibility probe; uv locks their transitive dependencies.
- The `pytorch-cpu` extra points to the official PyTorch CPU wheel index and is constrained to Python versions below 3.13. The tested Python 3.15 lane must not install PyTorch.
- `tool.uv.environments` limits resolution to Windows CPython 3.12 and 3.15. Python 3.13/3.14 and other platforms are outside this POC's compatibility claim.
- The generated lock contains artifact URLs and SHA-256 hashes. The lock must be generated by uv, never hand-authored.

- The first workload report from this clean environment recorded 28.52173 seconds total and 28.338949 seconds in the model stage. This was an outlier and is not representative of the repeated timings below.

- Temporal validation: `PASS`; chronological 80/20 split, one boundary row purged, 5,969 prior feature rows unchanged after future-data mutation, scaler fitted on training partition only.
- Sampled peak process RSS: 587,526,144 bytes; sampling interval 0.1 seconds. This is sampled RSS, not the OS absolute peak.
- The original 28.52173-second report recorded CPU time 10.109375 seconds and available memory before/after of 5,646,655,488 / 5,442,011,136 bytes. Its SHA-256 is `04722CC4D9E203E8C6F26E31FE14F536CF9B5EF14F67588DF8C97CE1B5099226`; the JSON remains local and has not been uploaded.
- A subsequent unprofiled run completed in 3.026026 seconds. A cProfile-instrumented run completed in 3.026026 seconds according to the workload's own timer; the profiler reported 9.555 seconds of profiled process time, so its timings are not directly comparable to the workload timer.
- Three additional consecutive unprofiled runs passed: 2.028404, 2.006837 and 2.024968 seconds (mean 2.020070 s; range 0.021567 s, approximately 1.07% of the mean). - The repeated runs show that the 28.52173-second observation was not reproducible in this sequence. Its cause is not established; it is retained as an outlier rather than silently discarded.
- The stage timer encloses all of `train_and_evaluate()`, while per-model fit/predict timers exclude scaling, model/tensor initialization and probability metric evaluation. Their totals are therefore not expected to equal the enclosing stage duration.

### Interpretation and limitations

Independent clean local reconstructions passed for both specified Windows CPython lanes, and CI run #17 completed successfully for HEAD `121c91cd705997345afce4ba12b54e2100445c50`, publishing machine-readable evidence for both locked reconstruction lanes. Three consecutive unprofiled Python 3.12 workload repetitions clustered tightly around 2.02 seconds. The earlier 28.52-second result remains an unexplained outlier, not a reproducible performance characteristic. This evidence supports repeatability only for the tested Windows x64 CPython 3.12/3.15 configurations.

The stage timer includes scaling, initialization and metric evaluation beyond the nested model fit/predict timers; this explains why those nested timings do not sum to the full model stage. The current instrumentation is adequate for this bounded POC but is not a fine-grained performance profiler.

The synthetic model scores (accuracy approximately 0.488–0.514) are execution smoke-test outputs only; they provide no evidence of BTC predictability, trading alpha, expected return or profitability. The evidence does not establish production suitability, cross-platform compatibility, or a technology baseline.

## Reproduce locally

Run from the repository root. Do not run both installations concurrently on a memory-constrained development machine.

### Python 3.12 + PyTorch CPU + quantitative workload

```powershell
$env:UV_PROJECT_ENVIRONMENT = Join-Path $env:TEMP "cpie-uv-312"
uv sync --locked --project ./poc/supply-chain/python --python "C:\\Users\\<user>\\AppData\\Local\\Programs\\Python\\Python312\\python.exe" --group compatibility --extra pytorch-cpu
uv run --project ./poc/supply-chain/python --locked --group compatibility --extra pytorch-cpu python ./scripts/poc/python_cpi_workload_probe.py --output (Join-Path $env:TEMP "cpie-uv-312-workload.json")
```

### Python 3.15 — compatibility imports without PyTorch

```powershell
$env:UV_PROJECT_ENVIRONMENT = Join-Path $env:TEMP "cpie-uv-315"
uv sync --locked --project ./poc/supply-chain/python --python "C:\\Users\\<user>\\AppData\\Local\\Programs\\Python\\Python315\\python.exe" --group compatibility
uv run --project ./poc/supply-chain/python --locked --group compatibility python -c "import importlib.util, sys, numpy, pandas, polars, pyarrow, sklearn, xgboost, lightgbm, scipy, statsmodels, fastapi, pydantic; assert importlib.util.find_spec('torch') is None; print('PYTHON:', sys.version); print('TORCH_INSTALLED: False'); print('IMPORTS: PASS')"
```

### Lock integrity and tree

```powershell
uv lock --check --project ./poc/supply-chain/python
uv tree --project ./poc/supply-chain/python --locked
Get-FileHash ./poc/supply-chain/python/uv.lock -Algorithm SHA256
```

Never use `git clean`, broad wildcard deletion or removal of the pre-existing virtual environments. If repeating the clean reconstruction, verify the exact temporary paths before deleting only those POC environments.

## CI validation

The reconstruction matrix is integrated into the existing default-branch workflow `.github/workflows/python-windows-compatibility-poc.yml`, rather than relying on a new workflow introduced by this PR. This avoids the GitHub Actions bootstrap limitation for newly added `pull_request` workflows.

- The existing workflow's path filters include the Python supply-chain manifest, universal lockfile and this POC documentation.
- A dedicated `uv-lock-reconstruction` job runs Windows CPython 3.12 and 3.15 matrix lanes.
- Both lanes pin uv 0.13.7, run `uv lock --check`, then `uv sync --locked`.
- Python 3.12 installs the PyTorch CPU extra, checks imports and runs the quantitative workload.
- Python 3.15 checks compatibility imports and asserts that PyTorch is absent.
- Each locked reconstruction lane writes a machine-readable evidence JSON with commit SHA, runtime/tool versions and step outcomes; both lane artifacts are uploaded. The Python 3.12 compatibility lane also uploads its workload report.

CI run #17 completed successfully for HEAD `121c91cd705997345afce4ba12b54e2100445c50`. Future changes to this PR must be validated against their own HEAD; a successful earlier run is not evidence for a later commit.
